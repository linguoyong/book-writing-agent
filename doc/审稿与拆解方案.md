# 拆解能力与审稿闭环 —— 可行性、改动量与优先级

> 2026-11-09。基于当前代码（`server/app` 46 个 Python 文件、`apps/desktop` 41 个 TS 文件）与
> 架构梳理结论。本文只做方案分析，不含代码改动。

## 结论摘要

| 问题 | 结论 |
|---|---|
| 开源拆解 skill 能否直接用于建专家 / 建公用知识库 | **方法论可用，代码不可直接安装**。适配成本高于收益，建议移植其拆解维度与分组策略，落到项目内 skill + 现有 `extract.py` 管线 |
| 审稿闭环是否需要 LangGraph 编排 | **单章的写-审-改不需要**，工具循环 + 落盘前 gate 就够；**批量多章流水线需要**，但应放在 P2，且更适合复用 `extract.py` 的后台任务模型而非对话线程 |
| 优先级 | 审稿（P0）> 审稿 gate（P0.5）> 拆解（P1）> 批量编排（P2） |
| 架构调整 | 5 处需要动，其中 `routes.py` 拆分与上下文装配参数化是前置条件 |

## 一、开源小说拆解 skill 调研

### 1.1 候选对比

| `tance-mang/chinese-webnovel-skills` 的 `deconstruct` | 单 skill + references | 拆平台爆款，输出可复用结构模板，明确「学结构不抄字」的原创底线 | 未确认 |

| `ekrenzin/Theseus` | 13 个 skill 的完整流水线 | 反向管线：EPUB → 章节 → 场景 → 风格 → 角色 → 情节 → 世界观，产物可直接喂创作管线 | 未确认 |

从「提取公用知识库」这个目标看，最贴近的是 **船板拆书**（有明确的分组策略和人物关系产物）和
**novel-characters**（有别名归并 + 证据校验，和本项目 `extract.py` 的思路几乎一致）。

### 1.2 为什么不能直接安装

三个硬性不匹配：

**运行环境不匹配。** 这些 skill 假设宿主有 shell、Glob 搜索、sub-agent 调度：

- 固定工作目录 `Factory/拆书/{书名}/`，靠 Glob 找书、找断点
- `fen-zhang-jie-gai-kuo` 依赖串行 sub-agent，`abc-fenxi` 依赖并行批处理
- `novel-characters` 依赖 Node 脚本与 `validate` 命令

本项目：无 shell 工具；文件后端是 `virtual_mode` 的 CompositeBackend（项目根 + `/global-skills` +
`/artifacts` 三段路由，无法访问 `Factory/`）；技能只认 `SKILL.md` + ASCII slug + 渐进披露；
没有把 LangGraph 子图暴露成「可被 skill 调用的 sub-agent」。

**产物格式不匹配。** 拆书 skill 输出 `章节概括.md`、`人物关系.yaml`、`事件线.yaml`、`ABC分析.md`；
本项目 KB 是 `characters / factions / items / locations / world / outline / materials / styles`
八类 frontmatter 卡片，带 `aliases`、`relations`、`timeline`。中间缺一层归一化，直接落盘会变成
两套并行的事实源，违背「Markdown 是唯一事实来源」。

**上下文假设不匹配。** 拆书 skill 习惯把整章甚至整组章节塞进一次调用；本项目已经为长文本设计了
480 字切片、60 字重叠、实体卡按 `##` 小节拆分、`chapter <= N` 防剧透下推。直接套用会绕开这些。

### 1.3 值得吸收的三件事

不是照搬流程，而是抄它的**判据**：

1. **「每 3 章一组、约 600 字」的分组摘要层**。当前 `extract.py` 是逐章独立抽取，跨章事件靠
   `_event_key` 字符串匹配去重，脆。加一层组级摘要，事件的因果链和伏笔回收会稳很多。
2. **ABC 爽点结构 + 钩子评估 + 情绪曲线**。这是审稿的现成评分维度，比「文笔好不好」可执行得多。
3. **人物关系的「角色地位 + 关系图谱 + 出场/完成/退场」**。与现有 `insight.py` 的关系图、
   `meta.relations` 直接对接，只差一个「地位」字段和弧光轨迹。

反面教训也有一条：`novel-characters` 用确定性脚本校验「evidence 必须是原文逐字片段」，
这个约束值得抄——LLM 抽取最容易出的问题就是编造引用，而当前 `extract.py` 没有这层校验。

### 1.4 落地路径（推荐）

不做「装 skill」，做「拆解能力」，分三步：

```
源文本 → 结构化拆解（JSON）→ 归一化 → 写入 KB 八类 + 生成专家/技能
```

**第一步：拆解调用。** 新增 `server/app/deconstruct.py`，骨架直接复用 `style_import.py`：
`_ask_model()`（走 `extractor` 模型 + 用量记账）+ `_parse_json()` + 落盘。差别只是 prompt 更长、
输出是多个数组而非单个 expert。

**第二步：schema 对齐。** 拆解输出必须对齐 `extract.normalize()` 的字段：
`characters / factions / items / locations / events / foreshadowing`，每个实体带
`name / aliases / summary / evidence / confidence`。这样能直接调 `apply_result()` 走现有的
别名归并、待确认队列、事件去重，**不用新写一套合并逻辑**。

**第三步：专家与技能。** 拆解结果额外产出两个文件，走 `experts.save_expert()` 与
`skill_write` 的同一格式：

- `experts/deconstruct-{slug}.md`：拆解专家，人设是「结构分析师」，不写正文
- `skills/abc-review/SKILL.md`：爽点与钩子评分方法（审稿复用）
- `skills/scene-rhythm/SKILL.md`：场景节奏检查清单（审稿复用）

即：**拆解产出的技能，第一受益人是审稿，不是写作**。这也是把拆解排在审稿之后的原因之一。

**改动量**

| 项 | 文件 | 行数 |
|---|---|---|
| 拆解服务（分章/分组、prompt、解析、归一化） | `app/deconstruct.py`（新） | 300 |
| 与 extract schema 对齐 + evidence 校验 | `app/deconstruct.py` 内 | 80 |
| 组级摘要写入 `extract.apply_result` | `app/extract.py` | +60 |
| API（预览 / 执行 / 进度 / 取消） | `app/api/routes.py` | +90 |

| 测试 | `tests/test_deconstruct.py` | +160 |
| **合计** | | **~990**（其中 160 行是提示词文本） |

不含前端重样式。若拆解只做「一次性导入、不要求进度条」，可砍掉 API 与前端的一半，约 **550 行**。

## 二、审稿闭环

### 2.1 现状缺什么

当前一个章节的完整生命周期是：

```
chapter_new → manuscript_write → interrupt（diff）→ 批准 → 原子落盘 → git
```

缺三样：

1. **判据**：没有「这一章算写完了吗」的标准，只有 `lint_consistency()` 做设定一致性检查
   （人名、别名、时间线冲突），不评结构、节奏、钩子。
2. **回路**：写完即结束，问题不会被反馈给写稿方。
3. **状态**：`book.json` 只有 `progress: {volume, chapter}`，没有章节级的 `draft / reviewing / passed`。

### 2.2 三条实现路径

| | A 工具内循环 | B 落盘前 gate | C 外层 LangGraph 编排 |
|---|---|---|---|
| 做法 | 写稿 agent 调 `chapter_review` 工具，工具内部独立调审稿模型，返回问题清单，agent 自己改 | 在 `manuscript_write` 执行前检查审稿状态，未 pass 则拦截 | 新建 `StateGraph`：write → review → 条件边 → revise → review，超轮次转人工 |
| 图改动 | 无 | 无（middleware / tool wrapper） | 大，需重做 thread 语义 |
| 强制力 | 弱（靠模型自觉） | 强 | 强 |
| 成本 | 低 | 低 | 高 |
| 风险 | 可能跳过审稿 | 快速改错别字也被拦，需要开关 | 打破「每轮重建图是廉价操作」的核心假设 |

**关键判断：C 不是必需品。**

`create_deep_agent` 返回的本来就是一张编译好的 LangGraph 图，`recursion_limit` 允许模型多轮
调工具。所以「写 → 审 → 改 → 再审」这个循环，用工具就能表达，不需要在图上再包一层。
加外层图真正换来的是：跨章批量的可恢复性、每轮审稿成为独立可观测节点、以及强制轮次上限。
这三件事只有「一次跑 20 章」时才值钱，单章写作不需要。

而且 C 有明确的架构代价：现在 `thread_id = session_id`，一张会话一张 checkpoint。加了外层图之后，
写稿子图和审稿子图必须各自命名空间（否则消息通道会串），`runner.chat_stream` 也要从「跑 agent」
改成「跑 workflow」，`runs.py` 的停止/恢复逻辑要跟着改。这是 P2 的活，不是 P0。

### 2.3 推荐方案：A + B，C 延后

**P0 · 审稿能力（工具内循环）**

```
写稿 agent 写完 → 调 chapter_review(chapter)
                    ↓
              review.py 独立调审稿模型（可配第三个模型来源）
                    ↓
              结构化问题清单：{p0:[], p1:[], p2:[], score, verdict}
                    ↓
              落盘：章节 front-matter 结论 + .index/reviews/ 明细
                    ↓
              返回给写稿 agent → 自己改 → 再审
```

要点：

- **独立模型来源**。现有 `writer` / `extractor` 两个配置，加第三个 `reviewer`。用不同厂商的模型
  审自己家的稿，能显著降低同源偏差。这是投入产出比最高的一行改动。
- **独立上下文**。不复用 `assemble()` 的 10 层（里面含「当前写作意图」，会污染审稿判断），
  新写 `assemble_review()`：设定卡摘要 + 前 2 章结尾 + 本章正文 + 评分量表。
- **证据校验**。问题清单里每条必须带原文引用，且引用必须能在本章逐字找到，找不到就丢弃该条。
  这条直接抄 `novel-characters` 的做法，能挡掉大部分幻觉批评。
- **审稿维度**（可配置，默认 6 项）：设定一致性（复用 `lint`）、结构完整性、节奏与场景推进、
  人物声音一致性、钩子与爽点、文字冗余。每项 1-5 分 + 最多 3 条具体问题。

**P0.5 · 章节状态机（gate）**

```
draft ──review──> reviewing ──pass──> passed
  ↑                    │
  └────fail────────────┘
```

- 状态写进章节 front-matter：`review: {status, round, score, reviewed_at}`。这是事实，进 git。
- 问题明细落 `.index/reviews/{chapter}.json`，是过程产物，可清。
- gate 放在 `manuscript_write` 执行前：若目标章节 `status != passed` 且本次是整章覆盖（`mode=overwrite`），
  弹出提示「本章未通过审稿（第 N 轮，P0 问题 X 条），仍要覆盖？」。给「继续」和「先看问题」两个选项。
- **不做硬拦截**。本地写作工具，硬拦会让人想砸键盘。默认提示，设置里可开「严格模式」。

**P2 · 批量编排**

只有当「一次推进 5-20 章」成为真实需求时才做。形态建议**复用 `extract.py` 的后台任务模型**
（`ThreadPoolExecutor` + `state.json` 断点 + `ExtractStats` 进度），而不是包 LangGraph 图：

```
for 每章:
  write_agent.ainvoke(...) → draft
  for round in 1..N:
    issues = review(draft)
    if pass: break
    draft = revise_agent.ainvoke(draft, issues)
  落盘 + 更新状态
```

对话式写作仍然走现有 `chat_stream`，两条路径互不干扰。这样既拿到了批量的可恢复性，
又不必重做 checkpoint 语义。

## 三、优先级排序

| 排序 | 事项 | 价值 | 成本 | 依赖 | 风险 | 建议 |
|---|---|---|---|---|---|---|
| 1 | 审稿能力（P0） | 高：补上「完成」的定义 | ~1100 行 | 无 | 低 | 立即做 |
| 2 | 章节状态机 + gate（P0.5） | 高：让审稿成为关卡而非建议 | ~330 行 | 依赖 1 | 低 | 紧随 1 |
| 3 | 拆解 → 专家 + KB（P1） | 中：服务开书阶段，收益间接 | ~550-990 行 | 依赖 schema 对齐 | 中（幻觉引用） | 1、2 稳定后 |
| 4 | 批量编排（P2） | 中：省人力，但单章没跑顺时无意义 | ~1000 行 | 依赖 1、2 | 中高 | 最后 |

排序理由：

- **审稿排在拆解前面**，不是因为它更「重要」，而是因为它卡住的是每天都要走的路径。拆解只在开书
  或引入对标作品时用一次。
- **拆解排在 gate 后面**，因为拆解产出的技能（ABC 爽点、场景节奏）正好是审稿的评分维度——
  先有审稿框架，拆解产物才有明确的落点；反过来做会产出一堆没人消费的报告。
- **批量编排必须最后**。单章闭环没跑顺就做批量，等于把未验证的流程放大 20 倍。

## 四、架构调整建议

按「是否卡住新功能」排序。

### 4.1 必改（新功能的前置条件）

**1. 上下文装配参数化。** `context.assemble()` 现在硬编码写作用的 10 层，`LIMITS` 与 `LABELS`
也是全局常量。审稿、拆解需要完全不同的层组合。建议把「层定义」变成数据：

```python
PROFILES = {
    "write": ["identity", "persona", "domain", "user", "long", "project", "parent", "references", "skills", "runtime"],
    "review": ["reviewer_persona", "domain", "chapter", "prev_tail", "kb_digest", "rubric"],
    "deconstruct": ["analyst_persona", "source", "schema"],
}
```

`assemble(project, profile="write", ...)`。改动集中在 `context.py`，约 120 行，不影响现有调用
（默认 `profile="write"`）。

**2. `routes.py` 拆分。** 1968 行 / 96 路由，加审稿和拆解会再涨 200 行以上。按域拆成
`api/routes/{projects,sessions,kb,review,admin}.py`，用 `APIRouter` 挂到同一个 `/api` 前缀。
纯机械重构，测试覆盖在，风险低。约 2 小时。

**3. 多 agent 的 thread 命名约定。** 现在 `thread_id = session_id`。一旦审稿需要独立对话历史
（P2 的 revise agent），必须约定 `{session_id}:review:{chapter}` 这类命名空间，否则 checkpoint
消息通道会串。即使 P0 不进图，也建议先在 `runs.py` 里把 thread_id 的生成收口成一个函数。

### 4.2 应该改（减少后续重复）

**4. `DomainPack` 协议太窄。** 现在只有 `build_tools`，表达不了「阶段」。审稿需要「只读 + 评审工具集」，
写稿需要「读写 + 审批」。建议扩成：

```python
class DomainPack(Protocol):
    id: str
    def build_tools(self, ctx: ToolContext, stage: str = "write") -> list[Any]: ...
```

`build_tools` 内部已经有 `readonly` 分支，加一个 `stage` 参数是渐进式的，不破坏现有实现。

**5. 后台任务层该抽出来。** `extract.py` 有 `state.json` + 断点 + `ExtractStats`，索引重建有
digest 账本，拆解和批量编排还会各来一套。建议抽 `app/jobs.py`：任务注册、进度、取消、断点。
`extract.py` 先迁移过去，后面三处直接复用。约 200 行，能省后面 400 行重复。

**6. 章节元数据缺「状态」维度。** `book.json` 只有 `progress`。建议加：

```json
"chapters": {
  "ch-001": {"status": "passed", "words": 3120, "reviewed_at": "2026-11-09T10:00:00", "score": 4.2}
}
```

文件树、进度条、导出、gate 四处都读它。不要放进 KB 八类——那是内容，这是进度。

### 4.3 不建议做

**不要引入 sub-agent 并发。** 拆书 skill 用 sub-agent 并行批处理来提速，但本项目是单用户本地、
LLM 调用串行、用量逐笔记账。并发会打乱用量归属，也让审批链复杂化。`extract.py` 的
`ThreadPoolExecutor`（`EXTRACT_WORKERS`）已经够用，保持一种并发模型。

**不要把审稿结果做成第九类 KB 卡。** 审稿是过程，不是设定。进 `book.json` 或 front-matter 的
状态位，明细进 `.index/`。否则 KB 会从「事实源」退化成「工作日志」。

## 五、建议的交付顺序

```
第 1 步（约 2 天）  context 参数化 + routes 拆分 + thread_id 收口
第 2 步（约 3 天）  review.py + chapter_review 工具 + reviewer 模型配置
第 3 步（约 1 天）  前端审稿卡（可先只做工具时间线里的富文本）
第 4 步（约 1 天）  章节状态机 + gate + 文件树徽标
第 5 步（约 3 天）  deconstruct.py + schema 对齐 + 两个技能种子
第 6 步（按需）     pipeline.py 批量编排
```

第 1 步是纯重构，不产生可见功能，但它决定了后面五步是「加文件」还是「改文件」。
如果只想先看到效果，可以跳过第 1 步直接做第 2 步——代价是 `assemble()` 会被临时改出分支，
后面还得回来收拾。
