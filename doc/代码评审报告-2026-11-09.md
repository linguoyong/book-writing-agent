## 项目理解与结论

这是面向长篇小说的本地桌面工作台：Electron 管窗口和后端启动，React/Zustand 管编辑与会话，FastAPI 提供业务接口，deepagents/LangGraph 驱动写作工具。Markdown 保存正文、设定和记忆，SQLite 保存会话、审批、用量与执行状态，FTS5/sqlite-vec 提供派生检索索引。

项目的优势是已经把写作流程落到了文件、差异审批、检索、记忆与版本历史上，最近还加入了独立审稿和作品拆解。原子文本写入、编辑冲突检查、会话执行锁、断连后继续生成、导航限制、依赖锁和 CI 也已经存在。2026-11-03 的旧报告不能直接作为当前缺陷清单；其中不少问题已经解决。

当前主要短板是跨功能的数据一致性和新增功能的入口验证。模块测试通过，但编辑器、Agent、审稿、检索分别操作同一份文件时，缺少统一的变更处理机制。建议先处理下面 8 项已复现问题，再扩展多章自动流水线。

## 已确认的问题

### 1. [P1] 审稿结束会覆盖等待期间保存的新正文

位置：[review.py](/D:/project/LC/book/server/app/review.py:309)，回写发生在该文件第 408 行。

`run_review()` 在模型调用前读取章节，调用结束后 `save_review()` 用当时的 `meta` 和 `body` 重写整个文件。期间没有检查文件版本、正文摘要，也没有在回写前重新读取当前内容。Agent 审稿与编辑器保存可以并行；审稿弹窗也可以在请求未结束时关闭。

复现：在假模型的 `invoke()` 中保存带 `USER_EDIT_DURING_REVIEW` 的新正文，再返回正常审稿结果。审稿完成后，该标记从磁盘消失，正文恢复成审稿开始时的内容。

影响：用户已保存的修改丢失。`save_text()` 的原子性只能保证文件完整，不能防止用旧版本覆盖新版本；此回写也未调用历史快照。

建议：审稿绑定正文摘要。写回时在文件级锁内检查当前版本，只合并审稿元数据；正文变更则把结果保留为历史记录并标为过期，禁止回写旧正文。单独在开始审稿时加锁还不够，所有写入入口必须遵守同一把锁或版本检查协议。

### 2. [P1] 桌面“拆解”入口启动后线程直接报错，任务永久显示运行中

位置：[common.py](/D:/project/LC/book/server/app/api/routes/common.py:698)。

`_deconstruct_worker()` 使用 `from .. import deconstruct`。该模块位于 `app.api.routes`，所以这条语句尝试导入 `app.api.deconstruct`，而实际业务模块是 `app.deconstruct`。导入语句还位于 `try` 外面，异常无法转成任务的 `error` 状态。

使用 FastAPI TestClient 调用真实入口得到：

```text
POST /api/projects/audit/deconstruct        -> 200
后台线程                                  -> ImportError: cannot import name 'deconstruct' from 'app.api'
GET /api/projects/audit/deconstruct/status  -> status: running，progress: {}
再次 POST                                 -> 409
```

影响：通过界面发起的拆解无法开始，停止请求也无法让已经退出的线程收尾；同一项目的任务状态会一直占用，直到服务重启。Agent 直接调用业务函数是另一条路径，不受此导入错误影响。

建议：修正相对导入层级，把初始化也纳入异常处理。补充实际启动路由、工作线程执行、状态收尾的接口测试；现有拆解单测直接调用 `deconstruct.run()`，OpenAPI 测试只验证接口结构，均覆盖不到这个错误。

### 3. [P1] 拆解工具绕过文件读取和知识库写入的 deny 规则

位置：[book.py](/D:/project/LC/book/server/app/domains/book.py:310)、[deconstruct.py](/D:/project/LC/book/server/app/deconstruct.py:352)。

`deconstruct_source()` 把绝对路径直接交给拆解函数，相对路径也未经过 `safe_join()` 和读权限检查。拆解再直接通过 `apply_result()`、`save_entity()` 等写知识库，没有沿用 `kb_write` 的 `_deny()`。自定义写入工具的审批名单也只列出了 `kb_write`、`manuscript_write`，见 [approvals.py](/D:/project/LC/book/server/app/agent/approvals.py:15)。

复现：在临时项目的 `.env` 放入假小说文本和假密钥标记，配置 `.env` 读取为 `deny`、`kb/**` 写入为 `deny`，通过实际 `StructuredTool.invoke()` 调用拆解。两个规则查询结果均为 `deny`，但假模型收到的提示词仍包含该标记，且磁盘上生成了 1 张角色卡。

影响：路径策略与实际能力不一致；接入远程模型时，被禁止读取的文件内容可以进入模型请求。拆解还会直接改变现有知识库和可选的专家、技能文件。

建议：区分“用户通过文件选择器明确选定的外部源文件”与“Agent 自行指定的路径”，为外部源建立授权记录；工具入口统一检查规范化路径和读权限，所有输出统一走写权限检查。需要审批的复合操作先生成可审阅结果，再落盘，不能仅靠工具描述中的使用约束。

### 4. [P1] 检索没有收录用户正在写的 manuscript 正文

位置：[search.py](/D:/project/LC/book/server/app/kb/search.py:286)。

`_scan_sources()` 只扫描 `kb/<kind>/*.md` 和 `chapters/*.md`，`_source_chunks()` 也仅处理这两类来源。`manuscript/` 不参与索引。

复现：项目中分别创建一张角色卡和带独有标记的正文章节，运行索引重建，再检查 `chunks.source`。结果只有 `kb/characters/person.md`，没有任何 `manuscript/` 来源。

影响：即使用户点击重建索引，Agent 的 `kb_search` 仍然无法召回自己刚写的章节，只能依赖直接读取文件或会话历史；这与长篇写作需要跨章回查的核心用途不一致。旧评审报告已记录过这一项，当前代码仍未解决。

建议：为自写正文增加独立来源标识和增量索引，统一章节号、卷号和防剧透过滤；明确导入原文与自写正文同时存在时的去重和优先级，避免两套第 N 章相互覆盖。

### 5. [P1] 在文件编辑器修改知识库后，检索仍使用旧卡片

位置：[files.py](/D:/project/LC/book/server/app/api/routes/files.py:94)。

通用 `PUT /file` 保存后直接返回，没有识别知识库路径并调用已有的 `_sync_kb_index()`。前端 `saveOpenFile()` 只刷新差异和概况，也不会重建索引。专用知识库接口和 Agent 的 `kb_write` 有同步逻辑，但通用文件入口绕开了它。

复现：先索引正文为 `OLD_CARD_SENTINEL` 的角色卡，再通过实际 `write_file()` 路由处理函数把它改成 `NEW_CARD_SENTINEL`。磁盘文件已更新，但 `chunks.text` 仍包含旧标记，不包含新标记。

影响：用户在文件面板纠正设定后，模型检索到的仍是旧设定，直到手工重建。即使 Markdown 是事实来源，也需要可靠地把变化传播给派生索引。

建议：统一处理文件变更事件，覆盖编辑器保存、Agent 通用文件工具、搜索替换、实体写入、导入、恢复版本和拆解；索引可异步更新，但应标记待同步或失败状态。

### 6. [P1] 改稿后“已通过”状态不可靠，列表与详情还会互相矛盾

位置：[files.py](/D:/project/LC/book/server/app/api/routes/files.py:106)、[review.py](/D:/project/LC/book/server/app/review.py:436)、[book.py](/D:/project/LC/book/server/app/domains/book.py:452)。

有两条已复现的路径：

1. 通过审稿后，调用编辑器的保存接口修改正文，列表和详情仍同时返回 `pass`。目前只有 `manuscript_write()` 会调用 `_mark_stale()`；搜索替换和通用文件写入没有同样的失效处理。
2. 显式调用 `_mark_stale()` 后，列表返回 `stale`，详情仍返回 `pass`。原因是详情优先读取 `.index/reviews/*.json` 中的历史结果，未与当前 front-matter 对齐。

影响：用户可能把已修改的章节误认为已通过当前版本的审稿；不同入口看到的状态也不一致。

建议：每份审稿结果记录正文摘要，用当前正文摘要决定是否有效；历史报告和当前状态分开返回。状态失效应由统一写入流程触发，读取时再校验摘要，以覆盖外部编辑器修改文件的情况。

### 7. [P2] 六维评分缺失五项时仍能判为通过

位置：[review.py](/D:/project/LC/book/server/app/review.py:352)。

缺失或非法评分被转成 0，计算平均分时却把所有 0 排除。`verdict` 的有效枚举也没有严格验证，只要不等于 `fail` 就可能通过。

复现：假模型只返回 `dimensions={"consistency": 5}`，其余五项缺失，问题为空且 `verdict=pass`。系统输出六项为 `5,0,0,0,0,0`，总分却是 `5.0`，状态为 `pass`。

建议：先用结构化模型验证六项全部存在且均为 1–5 的整数、问题结构合法、结论为明确枚举，再计算六项平均值。不完整输出应返回格式错误或请求重试，不能形成有效的“通过”。

### 8. [P2] 长章节只审了开头，也会被标记为整章通过

位置：[context.py](/D:/project/LC/book/server/app/context.py:90)、[review.py](/D:/project/LC/book/server/app/review.py:314)。

`run_review()` 先把正文裁到 40,000 字符，上下文装配的 `chapter` 层又只保留 16,000 字符。最终结果没有记录覆盖范围，也未因正文被截断而限制通过判定。

复现：创建超过 17,000 字符、尾部含 `UNREAD_TAIL_SENTINEL` 的章节。假模型实际收到的提示词不含尾部标记，但返回正常评分后系统仍把整章标记为 `pass`。

建议：显式限制单章审稿长度并提示用户，或按完整场景分段审阅后聚合；只有全章覆盖成功才能给出整章通过。覆盖范围和截断状态应进入报告，不能只在发给模型的文本里留一句截断说明。

## 进一步值得做的改进

1. **收敛文件变更流程。** 不必先大拆架构，先抽一个应用层写入服务，统一完成路径规则、版本检查、历史快照、原子写入、审稿失效和索引排队。它能同时解决多处一致性问题；现有原子写入函数值得保留。

2. **把测试重心补到真实入口。** 保留现有单元测试，再补少量“接口 → 后台任务 → 状态查询”和“审稿 → 改稿 → 读取状态”的流程测试。前端目前 19 个测试集中于格式化和 diff 纯函数，可优先增加项目切换、保存冲突、审批恢复的状态测试。Windows 桌面产品还应有 Windows CI 冒烟测试；当前两个 CI job 均在 Ubuntu 运行。

3. **让审稿获得与本章有关的具体设定。** 当前 `_kb_digest()` 每类按文件名顺序最多取 12 张卡，只取名称、别名和 `meta.summary/description` 的短摘要，不读取正文设定或 timeline 当前状态。设定仅写在 Markdown 正文时，审稿人可能只看到人名。可根据本章实体召回设定，按章节裁剪 timeline，并把引用来源带进问题报告。

4. **明确拆解的来源、范围和落点。** 当前留空源文件只选 `chapters/` 的第一份文件；在 3 份单章文件的验证中仅处理了 1 章。界面确实提示了“第一篇”，因此这不是隐藏行为，但作为整书拆解入口容易让人误解“3 组”的范围。建议支持章节范围选择，并把对标作品实体放在独立来源空间，避免按同名/别名归并到当前小说的角色设定。

5. **优先保存用户资产。** 明确备份正文、知识库、git 和业务数据库。`app.db` 中的会话、审批、用量、checkpoint 无法仅凭 Markdown 完整重建，不能和搜索索引一起称作可随时重建的派生物。历史快照也值得提供可见的恢复入口。

6. **校正文档的隐私表述。** README 的“模型、密钥、书稿都不出本机”与默认远程模型接口不一致。更准确的表述是“文件与配置保存在本机；使用远程模型或 embedding 时，相关文本会发送到配置的端点”。这一点不需要通过真实网络调用验证，配置和请求代码已能说明数据流。

7. **按页面拆分前端加载。** 本次 renderer 主 JavaScript 构建产物为 2,775.35 kB，App 静态引入各页面。可把知识图谱、用量、诊断等低频页面延迟加载，再用实际启动测量决定是否进一步优化。当前聊天页已经做了最近 60 轮折叠、memo 和导航抽样，不宜沿用旧报告直接认定它完全没有长会话优化。

## 建议处理顺序

先解决审稿覆盖新正文、拆解任务卡死和路径规则绕过；接着统一正文变更后的索引更新与审稿失效；最后收紧模型输出校验和审稿覆盖范围。

新增产品能力方面，优先做可恢复、可定位证据的单章“写—审—改”流程，等这些边界稳定后，再推进批量多章自动执行。
