## 1. P0：必须修（会持续损坏书稿 / 被接管 / 重复写入）

### P0-1　每次回写 Markdown 都多一层 `\r`（Windows 必然触发）

- 位置：`server/app/kb/repository.py:110`、`server/app/search_text.py:162`、
  `server/app/memory.py:132/146/148/150`、`server/app/domains/book.py:226`
- 成因：`read_text()`（`server/app/text.py:13-24`）原样保留磁盘上的 `\r\n`；
  而 `Path.write_text()` 在 Windows 上以 `newline=None` 打开，会把每个 `\n` 再翻译成 `\r\n`。
- 实测：

  ```
  b'a\r\nb\r\n'  →  read_text  →  write_text(text + 'c\n')
  结果： b'a\r\r\nb\r\r\nc\r\n'
  ```

- 触发面（都是高频路径）：
  - `manuscript_write(mode="append")` 读旧文再全量重写 → 每追加一次多一层 `\r`；
  - 逐章抽取每命中一次已有卡片就 `save_entity` 重写整张卡；
  - 正文搜索替换、记忆追加、项目记忆更新。
- 后果：文件逐次膨胀、git diff 变成"整文件重写"、导出 TXT 带 `\r`、
  front-matter 的 YAML 值被污染。不会立刻报错，因此极难察觉。
- 旁证：`2026-10-30` 的工作日志里已记录过"素材去重因 CRLF 失效"，当时的修法是在
  `_normalize()` 比对前统一换行——**只修了比对侧，写盘侧仍在翻倍**。所以这不是新引入的问题，
  而是同一根因的另一半。
- 修法：`read_text()` 读入即 `replace("\r\n", "\n")`（或所有写盘统一 `newline=""`），
  再写一个一次性迁移脚本把已有 `.md` 归一化。这是全项目改动最小、收益最大的一条。

### P0-2　Electron 没有导航守卫，令牌会交给任何被加载的页面

- 位置：`apps/desktop/src/main/index.ts:21-26`（`webPreferences`，`sandbox: false`）、
  `apps/desktop/src/preload/index.ts:20-27`（`backendInfo()` 返回 `token`）
- 缺口：没有 `will-navigate` / `will-redirect`，也没有 `setWindowOpenHandler`。
  preload 对每次导航都会重新执行，因此**被导航到的页面可以直接拿到 `port + token`**。
- 链路：把 `.html` 拖进窗口（Chromium 默认导航当前 webContents）或 Ctrl+点击渲染出的链接
  → 页面拿到令牌 → `POST /api/projects/open` 把任意目录注册成项目 →
  `PUT /api/projects/{id}/file` 读写任意文件 / `DELETE ?purge=true` 递归删除。
- 放大器：`server/app/main.py:37` 的 `allow_origins=["null"]` 正好放行 `file://` 页面；
  `POST /api/projects/open`（`routes.py:257-272`）接受任意绝对目录并顺手 `git add -A` + `commit`；
  `PUT /api/config` 可写入 MCP stdio 的 `command`，等于本机命令执行。
- 修法：`setWindowOpenHandler(() => ({ action: 'deny' }))` + `will-navigate` 一律拦截并转
  `shell.openExternal`（仅 http/https）；把令牌留在主进程，渲染层通过 IPC 代理请求；
  去掉 `allow_origins` 里的 `"null"`；开 `sandbox: true`。

### P0-3　未保存内容有四条静默丢失路径，且四个核心操作依赖 `window.prompt`

- `apps/desktop/src/renderer/src/store.ts:449-462`：`selectProject` 直接 `openFile: null`，
  不检查 `dirty`；`openFileByPath(..., force=true)` 又绕过唯一确认。
- `store.ts:845` / `:861`：保存成功后 `set({ openFile: { ...openFile, dirty: false, mtime } })`
  用的是函数入口的旧快照，**await 期间用户新打的字会被回滚**（磁盘也写回旧内容）。
- `apps/desktop/src/main/index.ts:43`：`window:close` 直接 `close()`，渲染层没有 `beforeunload`，
  主进程也没监听 `close`。有未保存修改时关窗 = 直接丢。
- `window.prompt` 出现在 `DiffPanel.tsx:77`（提交）、`FileTree.tsx:92/109/170`
  （新建文件 / 重命名 / 新建章节）。Electron 不实现 `window.prompt`，
  **这四个入口要么抛错、要么拿到 `null`，功能不可用**。
- 修法：所有"换文件/换空间/关窗"收敛到一个 `guardDirty()`；保存回写改函数式
  `set(s => s.openFile ? { ...s.openFile, dirty: false, mtime } : s)`；
  主进程 `close` 前询问渲染层；用受控 `PromptDialog` 替掉四个 `window.prompt`。

### P0-4　会话没有互斥，审批"先记账后执行"，写盘不是原子的

- `server/app/agent/runner.py:56-104`：`chat_stream` 只检查 `pending_approval`，
  没有会话级锁；`approve_stream`（`:265-370`）同样只读一次 pending 就往下跑。
  双击发送、开两个窗口、或"审批恢复"与"新消息"交叠，两个 run 会同时写同一个 `thread_id`。
  后果：消息重复/丢失；`Command(resume)` 撞上已消费的 interrupt；
  `manuscript_write(mode="append")` 把同一章追加两遍。
- `runner.py:315` 先 `db.resolve_approvals(status="approved")`，`:327` 才 `Command(resume=...)`。
  resume 抛错（条数不匹配、模型 401、权限谓词翻转、进程被杀）时，
  **UI 显示"已通过"，实际一次都没写**；且 `pending_approval` 已空，
  下一条消息会静默走进一个悬挂中断的 thread。
- `server/app/domains/book.py:216-231`：`manuscript_write` 是 `write_text` 直写（truncate + write），
  `append` 是 read-modify-write。进程在写盘途中被杀 → 原章节变半截/空文件。
  而 `versioning.py` 只在用户手动点"提交"时才留底，事故后无法恢复。
- 修法：进 `chat_stream` / `approve_stream` 前抢 `dict[session_id, asyncio.Lock]`，抢不到回 409；
  resume 成功后再 `resolve_approvals`，失败回滚为 `pending`；
  写盘改"临时文件 + `os.replace`"，并在写工具成功后自动 `commit_all` 一次快照。
