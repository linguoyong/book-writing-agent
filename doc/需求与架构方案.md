# 本地写作 Agent —— 需求与架构方案

> 版本 v0.1 · 状态：已确认，进入 P0 开发

## 1. 产品定位

面向长篇小说的本地写作工作台，三个核心能力：

1. **对话式写作**：Agent 能读稿、改稿、续写、查设定，写作过程可审阅。
2. **作品知识库**：角色、势力、物品、世界观、大纲、素材可维护，Agent 可随时读写。
3. **整本书导入**：TXT 解析 → 章节切分 → 逐章抽取 → 结构化入库 → 建立索引。

要解决的核心问题：通用 RAG 直接切块检索，搜不到小说设定。根因是结构化设定被当成普通文本切碎，缺少实体层与章节进度语义。

## 2. 界面结构（v0.3）

单栏对话 + 可收起的左右侧栏，专家、技能、知识库是独立整页。

| 区域 | 内容 |
|---|---|
| 顶部栏 | 左：侧栏开关、品牌、项目名；右：设置、右栏开关、最小化/最大化/关闭 |
| 左栏 | 新建会话；专家、技能管理、知识库三个入口；项目；历史会话 |
| 中栏 | 对话视图，或专家页 / 技能页 / 知识库页（由左栏入口切换） |
| 右栏 | Tab：文稿 / 知识库 / 文件 / 变更 / 侧问 |

主题：默认浅色（米白背景、白卡片、墨绿强调色），CSS 变量集中在 `:root`，预留 `[data-theme="dark"]`，后续在设置里切换。

### 2.1 侧栏交互

- 左右侧栏宽度均可拖拽（左 200–460px，右 280–480px）。
- 左右侧栏均可收起，收起后通过顶部栏按钮重新展开；右栏开关位于窗口控制按钮左侧。
- 左栏收起后，鼠标移到窗口左边缘会浮出左栏（覆盖式，移开自动隐藏），与 GPT 桌面端一致。
- 最简形态：左右栏都收起，只显示对话面板。
- 文稿不再占用左栏页签：点击文件树、知识库原文结果时，右栏自动展开并切到「文稿」。

### 2.2 专家、技能与写作风格

- **专家**是写作人设：具备简介、标签、写作风格 prompt 与工作流程正文，存放在项目 `experts/<id>.md`。
- 专家页是独立整页：卡片网格、搜索、当前专家标记、设为当前、对话创建。
- 输入框底部显示当前专家（专家选择器），点击跳到专家页切换。
- **技能**存放在 `skills/<name>/SKILL.md`，技能页展示已装技能、启用状态与路径，支持对话创建。
- 专家与技能都支持**对话创建**：进入对话视图后 Agent 会先提问确认定位，信息足够后调用
  `expert_write` / `skill_write` 写入文件，完成后回到对应页面即可看到。

### 2.3 @ 引用（设计，后续实现）

输入框输入 `@` 弹出候选面板，支持四类引用：

| 引用 | 作用 |
|---|---|
| `@文件` | 选择书稿文件，路径随消息发送，Agent 用读取工具打开 |
| `@角色` / `@势力` / `@物品` | 引用知识库实体，整卡注入上下文，显示出处 |
| `@章节` | 引用章节原文片段，用于续写与对照 |
| `@技能` | 显式激活某个技能，仅本次会话生效 |

实现约定：发送时附带 `references` 字段（类型、id、路径），后端组装上下文并在 UI 顶部显示引用条；未识别的引用不发送。

### 2.4 知识库页面（参考 Dify）

- **列表页**：八类知识库卡片（角色/势力/物品/地点/世界观/大纲/素材/风格），显示条目数与切片数，支持一键重建索引。
- **详情页**四个页签：
  - 文档：条目列表 + front-matter 与正文预览。
  - 切片：当前库的全部索引切片（标题、来源、章节、文本）。
  - 召回测试：检索参数面板 + 查询 + 命中结果（相关度分数、来源、片段）。
  - 设置：返回数量、最低相关度、检索模式（混合/关键词/向量）、关键词权重、章节上限；保存后作为默认参数写入 `kb/config.json`。

### 2.5 对话消息导航（设计，低优先级）

- 对话左侧显示一条细长导航条，每条用户消息对应一根短横线。
- 悬停显示该条消息的摘要浮层，点击滚动到对应消息并高亮。
- 消息数超过 8 条时出现，避免短对话干扰。

### 2.6 其他交互

- 侧问：独立 thread，只读检索，不污染主会话，结论可一键带入主对话。
- 变更审批：Agent 修改知识库或文稿产生 git diff，逐条 approve / reject。
- 上下文面板：显示本轮注入了哪些资料与来源章节。

## 3. 技术选型

| 层 | 选型 |
|---|---|
| 桌面壳 | Electron + electron-vite |
| 前端 | React 19 + TypeScript + Vite + Tailwind CSS + Zustand |
| 编辑器 | CodeMirror 6（Markdown） |

| Agent | deepagents（LangGraph 底座） |
| 模型 | OpenAI 兼容统一层，多 Provider 可配；写作模型与抽取模型分开 |

## 4. 数据布局

应用仓库（本仓库）只放程序代码。书稿数据独立存放，由用户选择目录。

```
<书稿项目>/
├─ book.json               书目元数据（标题、作者、进度指针等）
├─ manuscript/             当前写作的卷/章
│  └─ vol-01/ch-001.md
├─ chapters/               导入的原文（P1）
│  └─ 0001-第一章.md
├─ kb/
│  ├─ characters/          角色卡
│  ├─ factions/            势力卡
│  ├─ items/               物品卡
│  ├─ locations/           地点卡
│  ├─ world/               世界观条目
│  ├─ outline/             总纲、卷纲、章纲
│  ├─ materials/           素材（风景、人物、心理描写）
│  └─ styles/              写作风格卡
├─ .index/                 向量与检索索引（git 忽略，可重建）
└─ .git/                   该书稿的版本历史
```

原则：**Markdown 文件是唯一事实来源，索引是派生物，可随时重建。**

## 5. 知识库三层

### 5.1 档案层（Canon，结构化）

带 YAML front-matter 的 Markdown，字段固定。角色卡示例：

```markdown
---
id: char-lin
type: character
name: 林昭
aliases: [小林, 林师兄, 昭哥]
faction: faction-qingyun
status: alive
first_chapter: 1
tags: [主角, 剑修]
timeline:
  - chapter: 1
    state: { realm: 炼气三层, location: 青云山, mood: 隐忍 }
  - chapter: 48
    state: { realm: 筑基初期, location: 落霞城, mood: 决绝 }
    arc: 得知身世，与师门决裂
relationships:
  - target: char-su
    type: 同门
    note: 互相试探
---

## 外貌
## 性格
## 成长路线
## 备注
```

关键设计：**角色状态按章节版本化**。写作第 N 章时只注入 `chapter <= N` 的最新状态，避免剧透与状态错乱。势力、物品同理可带 `timeline`。

### 5.2 原文层（Evidence，RAG）

- 章节正文按章 / 场景切块，按段落与对白边界切分，保留 `chapter_id`、出场角色、地点、事件标签。
- 检索先做实体路由：命中角色 → 取档案卡 + 该角色出场章节片段，而不是全库盲搜。
- BM25 与向量结果用 RRF 融合，再按章节进度与实体过滤。

### 5.3 素材层（Material / Style）

- 风景、人物、心理描写片段，按场景类型、情绪、手法打标签。
- 写作风格卡：人称、句长、描写密度、口头禅、禁忌。
- 用途：写作时作为 few-shot 参考，可一键"收入素材库"。

## 6. 检索方案

1. **查询路由**：规则 + 轻量分类 → 档案检索 / 原文检索 / 素材检索 / 混合。
2. **档案检索**：精确键（name/alias/tag）+ FTS5，命中整卡注入。
3. **原文检索**：FTS5(jieba) + 向量，RRF 融合，元数据过滤（章节上限、实体、类型）。
4. **重排**：可选的 reranker（后续版本）。
5. **组装**：档案卡全文 + 片段 + 出处（章节号、文件路径），供 Agent 引用。

## 7. Agent 架构

- 基座：deepagents（planning / filesystem / subagents / skills / human-in-the-loop）。
- 文件后端指向当前书稿项目目录，Agent 直接读写 Markdown。
- 工具清单：

| 工具 | 作用 |
|---|---|
| `kb_search` | 三层混合检索，返回带出处的片段 |
| `kb_get` | 读取单个实体档案 |
| `kb_write` / `kb_patch` | 新增或局部修改知识库条目 |
| `manuscript_read` / `manuscript_write` | 读写当前章节 |
| `chapter_list` / `chapter_read` | 章节管理 |
| `git_status` / `git_diff` | 变更查看 |

- 上下文策略：不全量塞知识库。进度指针 + 检索 + 显式引用 + 本轮注入清单。
- 专家 / 技能：`skills/` 下的 SKILL.md，按需渐进加载；不同风格写手作为子 agent。
- 侧问：独立 thread_id + 独立 checkpoint，只读工具集。

## 8. 导入管线（P1）

1. **解析**：编码探测（UTF-8 / GBK）→ 章节规则识别（第X章/回/节、卷、序章、番外，规则可配）→ 清洗（页眉页脚、广告行、重复行、全半角、空行归一）。
2. **边界预览**：章节边界可视化，允许手动修正后再继续。
3. **落盘**：`chapters/0001-标题.md` + `book.json`。
4. **试抽取**：先跑 5–10 章，验收字段质量，再全量。
5. **逐章抽取**：后台队列、并发、断点续传、增量。Pydantic 约束输出：人物提及、新实体、状态变化、势力关系、地点、物品、事件摘要、伏笔。低置信度进待确认队列。
6. **实体归并**：别名 / 称谓合并，冲突人工确认后才并入 Canon。
7. **建索引**：章节 / 场景 chunk + BM25 + 向量 + 标签，输出导入报告。

## 10. 默认约定与风险

约定：

- 应用仓库与书稿仓库分离，书稿独立 `git init`。
- 向量索引放 `.index/` 并排除出版本控制。
- 嵌入默认关闭（仅 BM25 可用），设置中可启用本地 bge-m3 或 API。
- Agent 改动一律产生可审阅的 diff。

风险：

- 逐章抽取的成本与一致性，靠试抽取验收、断点与增量控制。
- 别名归并是质量瓶颈，必须保留人工确认环节。
- deepagents 版本变动，需锁版本并封装适配层。
- 百万字书的索引重建耗时，需后台任务与进度反馈。

## 11. P0′ 内核改造（已交付）

> 定位调整：从「小说写作工具」转为「通用桌面 Agent 内核 + 写作域包」。写作能力下沉为第一个域包，内核提供状态、记忆、装配与边界。

### 11.1 四层内核

| 层 | 实现 | 说明 |
|---|---|---|
| 状态 | `agent/checkpointer.py` | AsyncSqliteSaver，`thread_id = session_id`；历史由 checkpoint 驱动，不再手工拼消息 |
| 记忆 | `memory.py` | 用户 / 项目 / 长期三层文件 + 每日日志，显式写入 + 会话沉淀 |
| 装配 | `context.py` | 8 层装配 + 每层字符预算，产出可展示的注入清单 |
| 边界 | `domains/` | 域包持有工具与规则；写操作审批预留在 `interrupt_on` |

### 11.2 目录与数据

```
~/.book-agent/
├─ app.db                 # 业务表 + checkpoint 表
├─ memory/
│  ├─ USER.md            # 跨项目偏好（常驻）
│  ├─ MEMORY.md          # 长期记忆（按日期分节，带来源）
│  └─ YYYY-MM-DD.md      # 每日日志（追加）
└─ books/<书名>/AGENTS.md # 项目记忆（常驻，Agent 可编辑）
```

### 11.3 专家与技能

- **专家 = 人格**：`experts/<id>.md` 正文整份注入 system prompt（此前只注入一行 `prompt`）。frontmatter 增加 `max_turns`、`skills`。
- **技能 = 方法**：`skills/<slug>/SKILL.md` 通过 deepagents `skills=` 渐进披露——索引常驻，正文按需读取；技能名必须是 ASCII slug。
- **会话级专家**：`sessions.expert_id` 持久化，切换专家只影响当前会话，不再全局漂移。

### 11.4 记忆写入策略

- 显式：Agent 调用 `remember(text, scope)`，scope 为 `user` / `project` / `long`。
- 沉淀：右栏「上下文 → 把本会话沉淀到长期记忆」，抽取模型输出事实条目并标注来源会话。
- 去重：按前 80 字归一化比对；冲突不覆盖，新增并标注。
- 回忆：`recall_conversations` 对全量消息做 FTS5 检索，替代「把历史全塞进 prompt」。

### 11.5 升级注意

- 旧库自动迁移：`sessions.expert_id`、`sessions.domain`；消息表补建 FTS 索引。
- 新增依赖 `langgraph-checkpoint-sqlite`。
- 需重启后端进程以加载新内核；旧会话 `expert_id` 为空时回落到 `general`。
- 索引改为单实体增量：`KbIndex.reindex_entity`，写入不再全库重建。

## 12. P1′ 能力边界与引用（已交付）

### 12.1 写审批（HITL）

- **拦截**：deepagents `interrupt_on`，只拦 `kb_write` / `manuscript_write`；只读侧问会话不拦。
- **中断时**：计算 unified diff（新建 / 追加 / 覆盖分别处理），落 `approvals` 表，推 `approval` SSE 事件。
- **审批卡**：逐条 通过 / 拒绝（可填拒绝原因），支持「全部通过」；diff 按增删行着色。
- **恢复**：`POST /chat/approve` → `Command(resume={"decisions": [...]})`，沿用同一 checkpoint，工具随后真实执行。
- **约束**：pending 期间新消息被拒（避免并发改写同一 thread）；拒绝后模型被告知原因，不再重试同一调用。
- **未做**：`edit`（人工改参数后执行）与 `respond` 两种决策类型。

### 12.2 @ 引用

- **候选**：`GET /projects/{id}/reference-candidates?q=` 聚合八类实体、文稿、章节、技能。
- **注入**：`context.references` 层（6000 字预算）；实体整卡（front-matter + 正文），文件 / 章节 / 技能截断 4k，带 source。
- **前端**：输入 `@` 弹候选，回车选择；引用以 chip 展示、可移除；随消息发送并记入 message meta。

### 12.3 全局技能

- `CompositeBackend` 把 `~/.book-agent/skills` 挂到 `/global-skills`，与项目 `skills/` 一起作为 `skills=` 来源。
- 索引区分 `[项目]` / `[全局]`；同名技能后者覆盖前者（全局在前、项目在后 → 项目优先）。

### 12.4 验收

- 新建文件：审批前文件不存在 → 通过后写入；拒绝后仍不存在。
- 待审批期间新消息返回错误；审批记录 `approved` / `rejected` 落库。
- @ 引用：候选命中、`references` 层注入、模型按引用原文回答。
- 全局技能：模型 `read_file` 读取 `/global-skills` 并遵循技能内容。

## 13. 空间、轮次与引导（P0″，已交付）

### 13.1 空间（工作区）

- **概念**：空间 = 目录（`projects.path` 就是空间根目录），不再只是「数据库里的项目」。
- **左侧**：`空间` 分组显示名称、最近会话、会话数；下方 `会话` 只列当前空间。没有空间时点「新建会话」先要求创建/打开空间。
- **新建**：默认落点 `~/.book-agent/books/<slug>`，可用「浏览…」改到任意目录；目录即空间。
- **打开**：接入已有 `book.json` 目录；空目录则初始化为书稿空间（目录结构 + git）。
- **Electron**：新增 `dialog:pick-directory` IPC（preload `window.desktop.pickDirectory`）。

### 13.2 对话轮次

- 每轮 = 用户消息 + 执行过程 + 结论。
- 执行中：过程展开，头部显示「处理中 · 用时」。
- 完成后：过程折叠为「已完成 · 用时 · N 步」，只保留结论；点击展开完整步骤（工具名、状态、输入输出）。
- 结论取最后一个 assistant 文本，其余中间叙述归入过程。

### 13.3 查看变更

- 后端按轮收集写工具路径（`kb_write` / `manuscript_write`），生成本轮相对 HEAD 的 unified diff（未跟踪新文件也会生成），随 `done` 事件返回并写入消息 `meta.turn`。
- 轮次底部「查看变更 · N 个文件」→ 右栏「变更」页签显示本轮 diff，可一键切回「全部改动」。
- 历史轮次从消息 meta 恢复，刷新后仍可查看。

### 13.4 执行中引导（不打断）

- streaming 时输入框发送即「引导」：`POST /chat/steer`，消息入队并落库（`meta.steering`）。
- `SteeringMiddleware` 在每次模型调用前 drain 队列，以 `<steering>` 片段注入当前对话，不中断当前 run。
- 若引导晚于最后一次模型调用到达，当轮补一段跟进，避免留到无关的下一轮。
- 空闲时调用返回 409；待审批期间允许入队，恢复时消费。

## 15. 沙箱与权限（现状与计划）

### 15.1 现在的隔离到哪一步

| 能力 | 状态 |
|---|---|
| 工作区目录边界 | ✅ `FilesystemBackend(virtual_mode=True)` 拦截 `..`、`~`、越界绝对路径 |
| 敏感路径规则 | ✅ `.env` / `secrets/**` / 私钥默认 deny（见 15.4） |
| 通用文件写/改/删 | ✅ 先过路径规则，再走 HITL 审批（`/**` 兜底） |
| 知识库 / 文稿写入 | ✅ `kb_write` / `manuscript_write` 审批 + diff |
| 命令执行 | ⛔ 没有 shell 工具，不存在命令面 |
| 网络访问 | ⚠️ 仅模型/embedding 出站；Agent 无抓取工具 |
| 进程 / 容器隔离 | ❌ 无（与 WorkBuddy 同级别） |

### 15.2 WorkBuddy 是「每空间一个沙箱」吗

不是。本机 `settings.json` 的 `sandbox` 是一套**路径规则表**，不是容器：

- `orderedRules.file`：135 条 preset，按路径给出 `read / write / delete` 的 `allow / ask`（如 `~/.ssh/` 全部 ask，`~/.aws/` 读 allow、写 ask）。
- `orderedRules.command` / `orderedRules.network`：命令与网络各自一套规则，`networkDenyAllMigrated: true` 表示网络默认拒绝后按需放行。
- `extraAllowWrite`：给连接器单独放行的写入目录。

也就是说：**空间只是目录边界，隔离来自「路径规则 + 审批 + 命令/网络规则」，不是每个空间起一个 VM。**

### 15.3 我们需要什么

- 现在：不需要容器。**路径规则引擎**已交付（15.4）；后续把 `remember` 等固定写入点也收进规则体系。
- 引入 shell / 抓取工具时：必须同步上 P2 的**命令白名单 + 网络默认拒绝**，否则等于把主机交给模型。
- 容器化只在需要跑不可信依赖或多人共享机器时才有价值；单机写作场景成本高于收益，已确认不做。

### 15.4 路径规则引擎（已交付）

- **配置**：`config.sandbox.rules`，每条包含 `pattern / read / write / delete / note`；支持 glob，裸文件名（如 `.env`）自动匹配任意深度。
- **默认 7 条**：`.env`、`.env.*`、`secrets/**`、`*.pem`、`*.key`、`id_rsa*`（读/写/删全 deny）；`.git/config`（读 allow，写/删 deny）。
- **编译**：`compile_permissions()` → `FilesystemPermission` 列表；**声明顺序即优先级**（先匹配先生效），末尾追加 `/**` 写入审批兜底。
- **语义**：deepagents 只有 `read / write` 两类操作，delete 归入 write，所以一条规则的 write 与 delete 取更严格者；`ask` 映射为 HITL 中断。
- **实测**：`read_file /secrets/readme.md` 返回 `permission denied for read on /secrets/readme.md`；普通文稿写入仍需审批。
- **设置页**：模型设置 → 文件权限，可增删规则、逐项切换 `allow / ask / deny`，保存写回 `config.json`。

### 15.5 两种权限模式（已交付）

| 模式 | 行为 |
|---|---|
| **请求批准**（`ask`，默认） | `kb_write` / `manuscript_write` / `write_file` / `edit_file` / `delete` 都中断审批；规则里的 `ask` 也走审批 |
| **完全访问**（`auto`） | 跳过所有写审批，直接执行；**规则里的 `deny` 仍然生效**（`.env`、私钥、`secrets/**` 读写都被拒绝） |

- 会话级存储：`sessions.permission_mode`，输入框左下角切换，`PATCH /sessions/{id}` 持久化。
- 新会话默认取 `config.sandbox.default_mode`（设置页可改）。
- 自研写工具补了 deny 硬校验（`check_path`），避免完全访问绕过路径规则。
- 不做第三种「只读」：侧问本身已是只读工具集，普通对话没有这个需求。

## 17. Electron 托管后端（P1，已交付）

- **启动**：应用 ready 时 spawn `server/.venv/.../python -m uvicorn app.main:app`，端口优先 8787；被占用则自动取空闲端口。

## 19. 上下文窗口与自动压缩（已交付）

### 19.1 deepagents 本来就带压缩

`create_deep_agent` 在主 agent 栈里自动挂 `create_summarization_middleware(model, backend)`，不需要额外开启。它的默认策略分两种：

| 模型是否有 `profile.max_input_tokens` | 触发 | 保留 |
|---|---|---|
| 有 | 窗口的 85% | 窗口的 10% |
| 无（原来的 ChatOpenAI 就是这种） | 硬编码 170k tokens | 最近 6 条消息 |

`ChatOpenAI` 默认 `profile=None`，所以改造前实际跑的是「170k 触发、留 6 条」，和 500K / 1M 的窗口没有关系。

### 19.2 改成按窗口折算

- **配置**：`ModelSettings.context_window`，只给两个档位 `500000` / `1000000`，默认 500K；`PUT /config` 归一化到最近档位。设置页「上下文长度」下拉，仅此两项（其它模型暂不放开）。
- **模型**：`build_chat_model()` 把 `profile={"max_input_tokens": window, "max_output_tokens": 8192}` 挂到实例上，子 agent 的压缩中间件也读同一份 profile。
- **主 agent**：`agent/compaction.py` 构造同名 `SummarizationMiddleware` 传入 `middleware=`，deepagents 按 `name` 原地替换自带的那个（不会重复挂两个）。

| 参数 | 500K | 1M | 说明 |
|---|---|---|---|
| trigger | 400k | 800k | 到窗口 80% 触发摘要 |
| truncate | 275k | 550k | 先裁剪旧消息里的大参数（`write_file` / `edit_file` 正文），常常省掉一次摘要 |
| keep | 12 条 | 12 条 | 最近 12 条保留原文 |
| 摘要输入上限 | 60k | 60k | 只把淘汰区最近的 60k tokens 交给摘要模型 |

- **不丢东西**：被淘汰的消息在摘要前追加写入 `/conversation_history/<session>.md`，摘要里带路径，后续可用 `read_file` 回读；摘要输入裁剪只影响「摘要读到多少」，不影响落盘内容。
- **兜底**：服务端真超限抛 `ContextOverflowError` 时，中间件会先压缩再重试，不会把错误抛给用户。各家文案不统一（OpenAI 是 `context_length_exceeded`，DeepSeek 是 `maximum context length is N tokens`），`langchain-openai` 只认一部分，所以 `llm.BookChatModel` 在 `_generate/_agenerate/_stream/_astream` 四个入口把 400 翻译成同一个 `ContextOverflowError`；不相关的 400 原样抛出。
- **可见性**：`GET /sessions/{id}/context` 增加 `model` 与 `compaction`，右栏「上下文」顶部显示「窗口 500K · 400K 自动压缩」。

验收：切 1M 后接口返回 `{window:1000000, trigger:800000, truncate:550000}`；图内只有 1 个 `SummarizationMiddleware` 且 `trigger=('tokens', 800000)`；`_should_summarize` 在 trig-1 为 False、trig 为 True；`_should_truncate_args` 同理。

## 27. 知识库技术选型与实施路线（2026-10-30）

### 27.1 结论：sqlite-vec + 本地嵌入，全离线可用

**sqlite-vec 是嵌入式向量库**，不是服务：单个 C 扩展（Windows 下 `vec0.dll`），
在进程内由 SQLite 加载，数据与业务库同文件或同目录，没有端口、没有守护进程、
不需要 Docker / 独立部署。附带 `vec0` 虚表（KNN `MATCH ? AND k = ?`）与
`vec_distance_*` 标量函数，走 SIMD 暴力检索，不是 ANN 索引。

在本机实测（Python 3.13.5 / SQLite 3.49.1 / Windows）：

| 项 | 结果 |
|---|---|
| 扩展加载 | `enable_load_extension` 可用，`vec_version()` = v0.1.9 |
| 写入 | 5000 条 × 1024 维，0.31s |
| KNN top5 | 19ms（全库）；带 `kind` 分区过滤 10ms |
| 结果一致性 | 与纯 Python 余弦逐条一致（distance = 1 − cos） |

**代价**：`vec0` 表的向量维度在建表时固定，换嵌入模型必须重建索引（要有检测与提示）。

### 27.2 嵌入从哪来

现有中转（`172.21.122.93:48804`）只有 16 个对话模型，**没有 `/embeddings`**，
所以嵌入必须单独解决。实测了两条路：

| 方案 | 实测 | 取舍 |
|---|---|---|
| 本地 ONNX：`fastembed` + `BAAI/bge-small-zh-v1.5`（512 维） | 模型 91MB，加载 10.4s，编码 2 条约 10ms，纯 CPU | **默认**：装完即用，无 key、无外部服务 |
| OpenAI 兼容 `/embeddings` | 需要用户自备可用端点 | 可选：想上 bge-m3（1024 维）时用 |

网络现状：`huggingface.co` 直连超时（8s 无响应），`hf-mirror.com` 与
`www.modelscope.cn` 可达——首次下载模型要走镜像，代码里内置 `HF_ENDPOINT` 兜底。

### 27.3 实施顺序

先做知识库，再做导入：导入进来的东西最终要靠检索兑现价值，
否则「导了十万字还是搜不到」，等于白导。字数/进度排在 timeline 求值之前，
因为后者依赖前者提供「当前写到第几章」。

**第一段 · 知识库真实可用（4 个切片，一起验收）**

| # | 内容 | 关键点 |
|---|---|---|
| A1 | sqlite-vec 接入 | `vec0` 表（chunk_id 主键、kind 分区、chapter 元数据列、cosine）；替换 `vectors` BLOB 表并迁移；`reindex_entity` 同步 upsert/delete；维度变化检测 + 一键重建 |
| A2 | 本地嵌入落地 | `fastembed` + bge-small-zh（默认）/ API（可选）；设置页三选一 + 「测试」显示维度与耗时；首次下载走 hf-mirror，失败降级关键词并明示；重建索引显示 N/M 进度 |
| A3 | 分块与召回质量 | 实体卡按二级标题切小节（不再整卡塞进 512 token）；章节按场景/对白边界 400–600 字；实体路由（命中角色 → 整卡 + 出场片段）；RRF 权重可调、结果去重 |
| A4 | 可观测 | 召回测试同时显示关键词分 / 向量分 / 融合排名与命中来源；`index/status` 增加模型名、维度、构建时间、失败切片数；`kb_search` 返回里带命中原因 |

**第二段 · 整本书导入**

- 选文件（TXT/MD ≤ 50MB）→ 编码探测（UTF-8/BOM/GB18030）→ 章节正则（第X章/回/节、
  卷、序章、番外，规则可配）→ **边界预览**（首尾各 200 字，可合并/拆分/排除）→
  落盘 `chapters/NNNN-标题.md` + 更新 `book.json`。
- 导入即建索引（复用 A1），导完就能搜。
- 试抽取（先 5–10 章，人工验收字段质量）→ 全量逐章抽取（后台队列、断点续传）→
  实体归并候选（别名合并，人工确认后写 canon）。
- 明确不做：脚注、插图、复杂排版还原。

**第三段 · 成稿导出**

- `manuscript/` 按卷章顺序合并；TXT / Markdown / DOCX 三选一（DOCX 用 python-docx，
  带标题层级与目录）；导出前跑一遍 lint，把警告列出来。

**第四段 · 写作侧 P1**

| # | 内容 | 关键点 |
|---|---|---|
| D1 | 字数与进度 | `book.json.progress` 按 `manuscript` 最大章号自动推进；统计总字数/单章/日更/目标完成度；顶部进度条 |
| D2 | timeline 求值 | `kb_get` 与 @ 引用的注入按当前章取 `timeline` 最新状态（`state_at(chapter)`），彻底兑现「防剧透」 |
| D3 | 正文搜索/替换 | 复用 chunks 表，范围（当前章/全书）、正则、命中跳转 |
| D4 | 新建章节 | 文件树恢复 `ch-NNN` 递增 + 目标已存在检测 |
| D5 | 选中文本改写 | 编辑器选区 → 浮动条（润色/扩写/缩写/改语气）→ 流式结果按 diff 预览，确认后替换 |

**第五段 · P2**

- E1 版本历史：`git log` 列表 + 单次提交 diff + 单文件回滚（只读展示，不做分支操作）。
- E2 token 用量：按轮记录 `usage_metadata`，会话/项目汇总，成本可见。
- E3 素材「收入素材库」、关系图、时间线视图。

### 27.4 风险

- **首次启用向量要下载 91MB 模型**：失败不能挡住写作，必须降级关键词并给出可操作提示。
- **换模型 = 重建索引**：维度写死在 `vec0` 表里，迁移时按 `index_meta.model` 判断。
- **导入抽取的成本**：全量逐章抽取会烧 token，试抽取验收 + 断点续传是硬要求。
- **暴力检索的天花板**：10 万切片以内没问题；真要百万字以上再考虑 ANN（另起方案）。

## 28. 第一段落地：知识库真实可用（A1 / A2 / A4，2026-10-30）

### 28.1 向量底座换成 sqlite-vec

- `.index/search.db` 新增 `vec0` 虚表：`chunk_id` 主键、`kind` 分区键、
  `chapter` 元数据列、`embedding FLOAT[D] distance_metric=cosine`。
  旧的 `vectors`（float32 BLOB 全表扫）在建库时 `DROP`，索引是派生物，重建即可。
- KNN 走 `WHERE embedding MATCH ? AND k = ? AND kind IN (...) AND chapter <= ?`，
  `k` 用参数绑定；`kind` 用分区键过滤，跨类检索时一条 SQL 搞定。
- `vec0` 不支持 `INSERT OR REPLACE`（主键冲突），写入统一「先 DELETE 再 INSERT」。
- 维度写死在表结构里：`index_meta.vec_dim` 与当前模型不一致时重建空表并写回
  `vec_dim / vec_model`，`stats()` 额外返回 `expected_dim` 供界面提示「换模型了，要重建」。
- 章节上限过滤直接下推到向量检索，和关键词检索保持同一语义。

### 28.2 本地嵌入（默认档）

- `fastembed` + `BAAI/bge-small-zh-v1.5`（512 维、91MB、CPU）。可选
  `jinaai/jina-embeddings-v2-base-zh`（768 维、640MB，中文长文本更强）。
- 模型在进程内缓存单例，首次加载 2–10s，之后编码毫秒级；`HF_ENDPOINT` 默认指向
  `hf-mirror.com`（实测 huggingface.co 直连超时，镜像可用）。
- 设置页三选一：关闭 / 本地 / OpenAI 兼容 API；「测试连接」真跑一次编码并显示
  `维度 · 耗时`（实测 `512 维 · 42ms`）；改模型后会提示重建。
- 嵌入不可用（下载失败、接口报错）只记录 `last_vector_error`，不抛给对话，
  检索自动退化为关键词。

### 28.3 分块与去重（A3 的前半）

- 实体卡：正文 ≤ 700 字整张保留；更长时按 `##` 小节拆开并给每段加标题前缀，
  避免角色卡被嵌入模型截断（拆开后 id 为 `kind:entity:0/1/2…`）。
- 章节：切片从 600 字降到 480 字、重叠 60 字，贴近 512 token 的模型上限。
- 同一实体的多个切片在结果里只保留得分最高的一段；章节切片不去重。
- `reindex_entity` 改为整组替换（`DELETE ... WHERE id = ? OR id LIKE 'id:%'`），
  修复「拆开后再增量写入，旧切片残留成重复命中」。

### 28.4 可观测

- 召回测试每条命中显示 `关键词 #名次`、`向量 0.xxx`（余弦相似度）与融合分，
  能直接看出这条是被哪一路召回的。BM25 的绝对值随语料规模漂移（小语料只有 1e-6），
  所以展示名次而不是分数。
- `GET /projects/{id}/knowledge-bases` 的 `index` 增加
  `provider / model / dim / expected_dim / backend / error`。
- 重建索引返回 `stage / done / total`，页面轮询显示「重建中 128/1200」。

### 28.5 隐式路径不再阻塞

打开切片页、对话里首次检索这类隐式触发，只重建文本索引（`rebuild(embed=False)`）；
向量交给知识库页的后台任务和后续的导入流程。否则第一次对话会卡在整本书的向量编码上。

### 28.6 验收

- 单测 38 个全过（新增 9 个：vec0 写入/检索/分区/章节上限/维度切换/增量、
  长卡拆节/短卡不拆/整组替换/去重）。
- 真实书稿（长夜行，13 个切片）：`chunks 13 / embedded 13 / 512 维`，
  重建 6 秒内完成（模型已缓存）。
- 检索对比（同一查询）：「秩序洗牌是怎么发生的」关键词把《余温体系》排第一，
  向量把《世界格局：大洗牌》排第一，混合后《大洗牌》置顶——语义召回确实补上了盲区。

### 28.7 本段剩余

- **实体路由**：查询里出现角色名/别名时，直接把整卡提到前面并加权。现状是
  「晦是什么东西」这类问题，`晦（异兽）` 向量分最高（0.752）却因关键词分布被挤到第三。
- **alpha 调优**：默认 0.5 对中文小说偏关键词，考虑降到 0.4 并允许按项目保存。
- **reranker（可选）**：本地 `bge-reranker-base`，先留开关不做默认。
- 导入管线落地后，用十万字级语料重新评估切片长度与权重。

### 28.8 开发期 404：界面热更新了，Python 后端还是旧进程

现象：设置页「测试连接」报 `Not Found`，本地模型下拉是空的。

原因：前端走 Vite HMR 已经是最新代码，但 Python 后端是应用启动时拉起的进程
（uvicorn 没有 `--reload`，Electron 只在后端崩溃时才重启）。新加的
`/api/embeddings/options`、`/api/embeddings/test` 在旧进程里不存在，FastAPI 直接 404。

处理与加固：

- 杀掉旧后端进程，Electron 主进程 6 秒内自动拉起新进程（不需要重启整个应用）。
- `api.ts` 对 404 单独给文案：「接口不存在（path）：本地后端可能是更新前的旧进程，
  重启一次应用后重试」，不再把裸 `Not Found` 丢给用户。
- 模型列表读取失败时，下拉显示「模型列表读取失败」并禁用，不再静默空白。

顺手把本机默认切到本地向量并重建了两本书的索引：长夜行 13 切片 / 13 向量、
百廿时辰 3 切片 / 3 向量，512 维，无错误。清空模型缓存后从零测一次
`POST /embeddings/test`：**23.2s**（91MB 下载 + 加载 + 编码），返回 512 维。

## 29. 实体路由、alpha 调整与整本书导入（2026-11-02）

### 29.1 实体路由

查询里点名了某个实体，就该让它的档案排到最前——只靠 BM25/向量时，一张密集的总纲能压过角色卡本身。

- **名字表**：扫 `kb/*/*.md` 的 `name` 与 `aliases`，得到「名字/别名 → (kind, id)」；
  带 15 秒 TTL 缓存，知识库写入时（`reindex_entity`）立刻失效。
- **匹配**：名字按子串匹配（「林昭的剑」命中「林昭」，「晦是什么东西」命中单字别名「晦」）；
  虚词黑名单挡掉「的/是/他」这类单字，避免误伤。
- **加权**：命中的切片把分数抬到当前最高分 ×1.05，稳定排序保留命中实体之间的原有顺序；
  如果它压根没被两路召回，就从 `chunks` 表里取该实体第一条切片补进来（floor 分）。
- **边界**：只在请求的 `kinds` 里路由，不会把角色卡塞进「只搜大纲」的结果。
- 结果里带 `routed: true`，召回测试显示「命中实体」标签。

实测：`晦是什么东西` 从「总纲第 1、晦（异兽）第 3」变成「晦（异兽）第 1」。

### 29.2 alpha 默认 0.5 → 0.4

中文小说里关键词命中噪声大（专名、语气词反复出现），语义那一路应该多一票。
同步改了四处：`KbIndex.search` 参数、`DEFAULT_KB_CONFIG`、`SearchRequest` / `KbConfigRequest`、前端 `DEFAULT_CONFIG`。
已有项目若保存过 `kb/config.json` 仍按保存值走。

### 29.3 整本书导入

**解析**（`server/app/import_book.py`，无 LLM、纯规则）

| 步骤 | 做法 |
|---|---|
| 解码 | BOM → UTF-8 → GB18030 → 兜底替换；返回实际编码 |
| 章节识别 | 默认正则匹配行首「第X章/回/节/篇」「序章/楔子/引子/尾声/后记/番外」「Chapter N」；标题行超过 40 字不算，避免正文误判 |
| 卷 | 只作为分隔，不单独成章 |
| 兜底 | 完全没有标题时按段落切约 3000 字一节，保证能导入 |
| 卷首 | 不足 800 字丢弃，超过则单独成「开篇」章 |

**落盘**

- 文件 `chapters/NNNN-标题.md`，带 front-matter（`chapter / title / source / imported_at`）。
- 章号优先取标题里的数字（`第005章` → 5），缺失或重复时按「已有最大号 +1」顺延；
  已存在的章号算占用，**重复导入不会覆盖旧文件**。
- 文件名过滤 `\/:*?"<>|`，截断 40 字。

**接口与界面**

- `POST /projects/{id}/import/preview`：只解析不落盘，返回编码、总字数、章节列表（首尾各 80 字）。
- `POST /projects/{id}/import`：带 `excluded`（排除的章节下标）与 `titles`（改名），写完立刻起后台建索引。
- 前端「知识库 → 导入整本书」弹窗：选文件 → 预览（列前 300 章，可勾选排除、直接改标题）→ 导入；
  导入后轮询建库进度并显示「N/M · 约 X 分钟」。

**实测（《超神机械师》16MB）**

| 指标 | 结果 |
|---|---|
| 字数 / 章节 | 5,554,897 字 / 1,463 章（UTF-8，卷首 542 字被丢弃） |
| 预览 | 0.8s |
| 落盘 | 1,463 个文件，5.0s |
| 文本索引 | 12,409 个切片，约 50s |
| 本地向量 | 480 字切片约 135ms/条（16 核机器）→ 全书约 25–30 分钟（后台跑，可继续用） |

### 29.4 顺带修掉的问题

- **建库任务排队**：导入触发的建库还在跑时点「重建索引」会被 `running` 判断吞掉。
  现在第二次请求打 `queued` 标记，当前任务结束后自动再跑一轮。
- **章节标题重复**：检索结果里出现「第5章 第005章 轻装动力臂」。
  导入的标题本身带章号时不再加前缀。
- **预计剩余时间**：状态接口加 `eta_seconds`，按钮显示「重建中 128/12409 · 约 25 分钟」，
  避免几十分钟的任务看起来像卡死。

### 29.5 本段未做

- 逐章抽取（人物/地点/事件/伏笔）与实体归并：需要 LLM，按「试抽取 5–10 章验收 → 全量 → 断点续传」推进。
- 预览里的合并/拆分章节：目前只支持排除与改名。

## 30. 逐章抽取与实体归并（2026-11-02）

导入把正文搬进来，抽取把正文变成设定。

### 30.1 抽取

- 每章截前 6000 字，用**抽取模型**（`extractor`，建议便宜稳定的模型）输出固定 JSON：
  角色 / 地点 / 势力 / 物品（`name / aliases / role / note / confidence`）、
  事件（`summary / characters / importance`，最多 3 条）、伏笔（最多 2 条）。
- 输出做三层兜底：取第一个 `{...}`、`normalize()` 限长限条数、置信度夹到 0–1。
- 落库状态记在 `.index/extract.json`，按章号跳过已抽章节，**断点续传**；
  失败单独计数，下次重跑会重试这些章。

### 30.2 实体归并

| 情况 | 处理 |
|---|---|
| 名字或别名命中已有实体 | 只把新别名并进 front-matter，**不动正文**，避免覆盖人工内容 |
| 没有命中 | 建 stub 卡：`status: 待确认`、`source: auto`、`first_chapter` + 「自动抽取」小节 |
| 事件 | 追加到 `kb/outline/auto-timeline.md`：`- [事件][第N章] 摘要（人物）` |
| 伏笔 | 同文件：`- [伏笔][第N章] 文本`；任务收尾按章号重排一次 |

整张实体表（名字/别名 → 卡）在任务开始时扫一次，新建时就地写回，避免逐章重扫目录。

### 30.3 并发与成本

- LLM 调用并发（`EXTRACT_WORKERS = 6`），**落库串行**：同一张卡不会被两个线程同时改写。
- 实测（deepseek-v4.1-flash 中转）：单章 50–80 秒，6 并发下 3 章约 50 秒；
  5.5M 字（1463 章）全书量级 **4–6 小时**，可随时停止、下次续上。
- 5 章实测产出：8 角色 / 13 地点 / 7 势力 / 20 物品 / 8 条别名合并 / 15 事件 / 10 伏笔，0 失败。

### 30.4 界面

知识库页「抽取设定」：进度条（已抽 N/M）、七项统计、样例标签、
试抽取 3 章（`dry_run`，只统计不落盘）、开始/停止、待确认队列。抽取完成后自动重建索引。

### 30.5 补齐的三点（同日第二轮）

**a) 待确认队列**

- 新实体置信度 < 0.55，或别名已属于另一个实体 → 写进 `.index/extract-candidates.json`，**不落库**。
- 候选 id 为 `kind:entity_id`，重复入队自动去重。
- 弹窗里逐条列出「名字 + 第N章 + 原因 + 一句话描述」，可采纳/忽略；
  采纳即建卡，并在**后台线程**单独建索引——首次会加载嵌入模型，同步做会把按钮卡十几秒。

**b) 实体正文的增量合并**

- 已有卡片不再只合别名，每章的 `note` 会追加到自动管理的小节：

  ```
  ## 自动摘要
  - 第7章：第一次改装机械臂
  ```

- 只动这一节，人工正文一字不改；同一章只留一条（幂等），最多保留最近 20 条，
  长书不会把卡片撑爆。

**c) 事件去重与冲突检测**

- 事件 key = 去掉标点后的前 24 字，跨章节去重；重复的计入 `duplicates`，不写时间线。
  key 持久化在 `extract.json.event_keys`，重跑全书也不会重复。
- 别名冲突（别名已属于别的实体）不硬并，转待确认并注明「别名 X 已属于 Y」——
  这是「同名不同人」最典型的信号，硬并会毁掉两张卡。
