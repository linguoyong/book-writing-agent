# 流式超时恢复回归

## 现场结论

只读核对真实会话的消息元数据与 LangGraph checkpoint：本轮累计 207,903 ms（3 分 28 秒），14 次工具调用均为读取、列举或检索，没有写入。模型为 `deepseek-v4.1-flash-1017`，失败节点为 `model`，错误为 `StreamChunkTimeoutError`：已经收到 5,635 个流式块，此后连续 120 秒没有新块，触发 SDK 的流式看门狗。

这是模型响应阶段超时；已有证据不能进一步判定上游为何停止发送。原有 HTTP 请求超时 180 秒与流式块间隔超时 120 秒是两个独立设置。本次保留 120 秒保护，不通过取消超时掩盖问题。

此前错误只通过 SSE 临时发送，没有持久化；主对话随后从历史恢复时把具体错误替换成了“已中断”。流结束还可能再追加一条笼统的中断提示。

## 修复

- 主模型发生流式块超时时，检查 checkpoint：仅允许单个失败的 `model` 节点、没有审批中断且能定位该次模型输出起点时恢复。同一段执行最多自动重试一次，使用原 checkpoint 继续，不重复提交用户消息，不重放成功工具。
- 重试前撤回失败模型的半截文本，SSE、运行快照、主对话及侧问保持一致；按 Unicode 码点计算，包含 emoji 的文本也能正确撤回。界面明确提示正在重试，历史摘要保留重试次数。
- 持久化 `turn.error.message/code`，即使模型没有输出任何文字也保存失败轮次。具体原因显示在折叠过程之外，刷新后可见。SSE 已有明确错误时不追加另一条通用错误。
- 审批后的工具已成功、总结阶段才超时时，审批正确记为已消费。工具/子代理内部超时及用户主动停止不自动重试。

## 验证

`pnpm check` 通过：后端 340 项、前端/桌面 68 项，以及 lint、类型检查和生产构建。

新增 HTTP 集成测试运行真实应用、代理、文件工具、审批和 SQLite checkpoint，仅模型服务为确定性故障注入；测试环境将流式间隔缩短为 1 秒：

| 场景 | 结果 |
| --- | --- |
| 追加正文后模型超时一次 | 自动恢复并生成最终总结，正文标记仅出现一次，工具只执行一次 |
| 连续两次超时 | 只重试一次，然后明确失败；历史保留错误类型和原因 |
| 未产生任何文本就超时 | 主对话/侧问仍保存失败记录 |
| 审批写入后总结连续超时 | 写入不重复，审批不残留 pending |
| 失败模型含 emoji 的半截输出 | 正确撤回，运行快照与最终历史没有重复的半截文本 |
| 工具超时、用户停止 | 不触发自动重试 |
| 主对话及侧问展示 | 共用组件显示具体原因，位于默认折叠过程之外 |

界面使用隔离 `BOOK_AGENT_HOME` 与测试空间，没有修改真实书稿或真实会话。自动恢复不能保证上游模型下一次必定响应，超过一次重试仍失败时由用户决定稍后继续。

打包后的冻结后端另通过 32 项真实 HTTP 集成验收，包含上述四个超时场景及既有审批、权限、检索、导入、审稿、版本与会话恢复。安装版隔离启动、认证、后端崩溃自动恢复、正常关闭均通过；测试前后真实用户数据库、配置及 PID 记录指纹一致。程序直接覆盖指定目录，不备份旧程序；逐文件 SHA-256 核对一致。主对话和侧问界面截图保存在本地 `.screenshots/stream-timeout-recovery-20261110.png`，图中 1 秒超时仅用于故障注入，正式程序仍为 120 秒。
